# R4-Claude: Contract Schema v0.2 for agent mode

**Core position:** verify the extracted patch, not the workspace. The Worker is autonomous while it authors changes. The controller then extracts the diff, rejects out-of-scope paths, applies the rest to a clean copy, and runs checks there under its own identity. This gives most of patch mode's integrity guarantees while keeping agent autonomy. It protects result integrity but does not prevent side effects such as credential reads or network calls. Those need real isolation.

## 1. Rulings on GPT R4

| Item | Ruling |
|---|---|
| Worktree ≠ sandbox | **Accept.** Detection-only is not enough for medium/high tiers. |
| Three modes (Development / Restricted / Privileged) | **Amend.** Replace them with capability requirements. A mode is just a named preset of requirements, and the controller can check requirements. |
| `network: deny_requested` | **Reject as written.** A cloud-model agent needs network access to reach its own provider, so "deny" is unsatisfiable. The real policy is `egress_provider_only`, which needs a proxy or firewall rule. I haven't verified how to do this on Windows, so it needs a spike. |
| Requested vs. enforced | **Accept, and make it fail-closed.** If a requirement isn't proven, dispatch is refused unless the Owner records an exception. |
| Privileged mode | **Fold into exceptions.** An exception names the exact capability waived, applies to one task, and is granted only by the Owner. |
| "Never delegate policy or final verification" | **Accept as an invariant.** |

## 2. The four disagreements

**1. Command enforcement.** We can't intercept every internal action, so enforce at the boundary and layer the rest:

| Layer | Mechanism | Status |
|---|---|---|
| Boundary | Separate low-privilege OS user with NTFS ACLs, or a container with only the worktree mounted | **Enforced** (once probed) |
| Environment | Spawn the Worker with an allowlisted env, so no inherited secrets beyond its own provider key | **Enforced**, cheap |
| Agent-native permissions | The CLI's own allow/deny settings | **Best effort.** Treated as defense in depth, never as a guarantee. |
| Detection | Tree hashes, out-of-scope diff, process audit | **Detective** |

- `allowed_commands` becomes `commands_hint`, advisory unless a backend declares enforcement.
- **Capability probe, not config trust:** at startup the controller runs a probe as the Worker identity. It tries to read the controller DB, write outside the workspace, and read an env secret. The result is stored as the enforcement manifest. `requires ⊆ proven` or dispatch is refused.
- **BLOCKED sources:** a Worker report declaring blocked, or a permission-denied event from the agent's log. Both are adapter-specific. My assumption is that headless agents deny out-of-policy requests by default; this must be verified per agent.

**2. Hidden-check isolation.**
- Hidden payloads live in the controller store, outside the Worker identity's reach, and are never in the worktree during the run.
- They are materialized only in the scratch verification copy, **after the Worker is confirmed dead**.
- **Test-config tampering:** a Worker can edit `conftest.py`, `pytest.ini` or `pyproject.toml` to make tests pass. Extract-and-verify closes this, because only paths in `scope.write` are applied to the scratch copy, and test-config files are `frozen`.
- **Honest limit:** without OS-level isolation (same OS user), hidden checks are unprotected. Evidence from them is tagged `hidden_unprotected` and counts as weak.

**3. Crash vs. lost report.** Don't rely on the Worker's report at all, since verification derives from workspace state.
- **Liveness comes from the controller's own process handle.** On Windows I'd use a Job Object with kill-on-close. If the controller dies, the Worker tree dies, so the "orphan still running" case mostly can't occur.
- Record in events: PID, process creation time, job handle ID, and a per-dispatch `attempt_id` (the fencing token).
- On restart:
  - Process absent, or creation time mismatched → dead.
  - Process present and match → kill the tree and confirm.
  - Can't confirm → state `UNKNOWN_LIVENESS`: don't touch the workspace and don't re-dispatch; wait for a timeout, then escalate.
- **A new attempt always gets a fresh worktree from the checkpoint.** Two writers can't share a workspace, and any report carrying a stale `attempt_id` is discarded.

**4. Passing tests ≠ objective.**
- Outcomes have a verification type. `executable` outcomes need a live, admission-validated check. `manual` outcomes carry an `owner_check`.
- **Worker-authored tests don't count as evidence.** In agent mode the Worker will write tests, and that's fine, but they are excluded from outcome verification unless adopted in an amendment.
- **Objective-level check:** at tier ≥ medium, at least one end-to-end check run per task.
- **Outcome states:** `verified | weak | unverified | contradicted`.
- **Task states:** `DONE_VERIFIED` requires all executable outcomes verified. Any manual outcome leaves the task `AWAITING_OWNER_ACCEPTANCE`. The report lists unverified items first.
- Only the controller can set an outcome to `verified`.

**SQLite consistency:**
- One writer, the controller. The DB sits outside the Worker's reach.
- WAL with `synchronous=FULL`.
- The event and the projection update commit **in the same transaction**, so state tables can't diverge from the log. A replay check can rebuild them.
- Intent event committed → side effect → outcome event. Intents carry a `UNIQUE(attempt_id, action)` idempotency key.
- A startup reconcile pass resolves every intent that has no outcome.

**Changes from R3:**
- `execution.requires` replaces modes.
- `verification` block added.
- Manual outcomes added.
- `frozen_paths` extended to test config.
- `per_attempt` limits added.
- `authored_by` added on checks.
- `owner_acceptance` gate added.

**Runtime-only (never in the contract):**
- `attempt_id`, PID, creation time, job handle
- the enforcement manifest and the resolved requires-vs-proven diff
- tree hashes, checkpoints, incidents
- resolved model IDs, costs, outcome statuses

## 4. Mandatory for v0 vs. deferred

| Mandatory | Deferred |
|---|---|
| Fail-closed requires-vs-proven check, with probe | Per-tool-call interception |
| Extract-and-verify with frozen test config | Rich result parsing |
| Job-object process ownership, `attempt_id` fencing | Parallel workers |
| Fresh worktree per attempt | LLM reviewer (keep the hook) |
| Env scrubbing | Hidden-check rotation, mutation testing |
| Worker-authored tests excluded from evidence | Non-git snapshots |
| Single-writer SQLite, intent/outcome transactions | Advisory triage LLM |
| `egress_provider_only` as a requirement | A second provider adapter (interface only) |

## 5. Roadmap with exit criteria

| Phase | Scope | Exit criterion |
|---|---|---|
| **P0 Feasibility spike** (needs your authorization) | Prove enforcement on your machine: a separate user or container, kill-tree, headless agent run, scrubbed env | The probe suite passes: the Worker can't read the controller DB, can't write outside the workspace, sees no env secrets, and the killed tree is confirmed dead |
| **P1 Controller core** | SQLite events and projections, admission with baseline run, state machine, a fake Worker script, no LLMs | Crash injection at every intent/outcome boundary recovers cleanly |
| **P2 Real Worker adapter** | One step, a hand-written contract, extract-and-verify | A seeded out-of-scope edit and a seeded test-config edit are both rejected |
| **P3 Planner role** | LLM-authored contracts, plan approval, coverage report | The Planner's contract passes admission, and unverified outcomes are listed first |
| **P4 Retries and hidden checks** | Failure classes, two-stage retry, hidden checks if P0 proved isolation | Seeded failures route correctly with no infinite loops |
| **P5 Extensions** | A second provider, the reviewer LLM | Deferred until P1-P4 are stable |
